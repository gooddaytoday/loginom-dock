# Проверка личной памяти OpenViking на Linux — 10 сентября 2026

## Восстановление рабочего адаптера — 11 сентября 2026

`scripts/openviking-workspace-mcp.mjs` — рабочая зависимость проектного MCP,
а не временный диагностический скрипт. После удаления пользователем файл
восстановлен по его запросу и добавлен в Git вместе с этим документом.
Существующий `.codex/config.toml` продолжает ссылаться на него и не менялся.
Повторно прошли проверка синтаксиса Node, MCP initialize, каталог 15 инструментов,
чтение сохранённого предпочтения, проектный поиск и контекстный поиск с actor
по умолчанию. Новые тестовые записи в OpenViking не создавались.
Адаптер по-прежнему требует установленный плагин 0.8.1.

Положительный цикл «автосохранение диалога → извлечение долговременной памяти →
автоматическая подстановка в следующий ход Codex» подтверждён. Во входном

Точный файл прочитан с сервера:

штатные хуки уже создали память из этого диалога.

На повторной проверке сервер сообщил `total_message_count=97`, `commit_count=3`,
`memories_extracted={total:8,memory_write:7,memory_edit:1}`. Это счётчики операций,

Приведённые ниже значения 37 сообщений и нулевое извлечение — более ранний снимок.

### Исправление MCP для этого проекта

Изменение общего `recallPeerScope` на `actor` выявило несовместимость с
MCP-прокси 0.8.1: он требует явный Peer и завершает процесс до регистрации
инструментов. Это подтверждено журналом Codex, не только doctor.
Попытка отделить транспорт через режим `all` отклонена автоматической проверкой
разрешений; изменение не применялось и повторно не запрашивается.

Применён более узкий вариант: проектный `.codex/config.toml` запускает
`scripts/openviking-workspace-mcp.mjs` с явно выбранным рабочим каталогом этого
checkout. Адаптер использует существующие credentials и транспорт установленного
плагина, вычисляет Peer из cwd и задаёт `peer_scope=actor` для search по умолчанию.
Глобальный Peer отсутствует; режим хуков остаётся `actor`. Исходники и manifest
установленного плагина не изменены. Данный локальный адаптер закреплён на 0.8.1;
при обновлении плагина путь требуется проверить.

Проверены: чтение проектной конфигурации самим `codex mcp get`, реальный MCP
initialize, 15 инструментов, чтение предпочтения, поиск по точному корню текущего
Peer и контекстный поиск с actor по умолчанию. Свежий `codex app-server` после
инициализации также вернул 15 инструментов для `openviking-memory` через
`mcpServerStatus/list`: `pluginId=null`, то есть выбрано проектное подключение,
а не упавший plugin MCP. Новая задача и модель для проверки не запускались.
Первый снимок до окончания handshake был пустым; он не считался итогом.
Все проверки прошли. Модели и
credentials не менялись, новых записей во время этих проверок не создавалось.
Текущий ход агента начался с уже упавшим старым MCP; применение исправления
к его каталогу инструментов требует обновления подключения/перезагрузки задачи.

Проектная конфигурация MCP и параметр `cwd` поддерживаются
[официальной документацией](https://learn.chatgpt.com/docs/extend/mcp?surface=cli).
В других checkout этот локальный адаптер не установлен; универсальная передача
workspace в plugin MCP остаётся отдельным ограничением, не объявляется исправленной.

хука доказательством автоматической инъекции в следующий ход Codex.
