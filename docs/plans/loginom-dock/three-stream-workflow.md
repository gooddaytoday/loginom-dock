Она использует уже готовую основу и может разрабатываться независимо.

у 16 — точные значения переменного типа, включая ответ `user-v1`.
Окончание одного потока не требует ждать остальных, но следующий узел сам не запускается.
Ревью готового кандидата может идти одновременно с разработкой других узлов.

Полные требования остаются в индивидуальных подпланах. В частности, 12 размечает
все строки и не удаляет дубликаты; 11 не подменяет признак `_Replaced` сравнением
значений; 13 проверяет нативные границы календарных периодов. Упрощать эти требования
ради параллельности нельзя.

Предпочтительны постоянные worktree: один узел — одна ветка — один каталог.
Обычная задача приложения должна работать именно в этом каталоге. На подготовке
проверить способ регистрации/открытия такого проекта в текущем приложении.
Если используются worktree, созданные приложением, до разработки закрепить
именованную ветку и сохранность каталога при закрытии задачи.

Проверка запуска показала, что архивирование задачи удаляет временный worktree
приложения даже при наличии Git worktree lock. Для рабочих потоков выбран
постоянный каталог `.worktrees/node-*`, открытый как самостоятельный проект через
`codex app <path>`, и задача в его local environment. Временные подготовительные
задачи оставлены в архиве; в них код обработчиков ещё не менялся. Ветки сохранены
и восстановлены в постоянных каталогах. Рабочие чаты не архивировать ради reload.

Первую тройку ответвить от одного принятого main. Каждый последующий узел получает
новую ветку от отдельно записанной принятой базы; автоматически наследовать
необъединённый предыдущий узел нельзя. Для 15 использовать независимый CSV с готовыми
календарными полями, пока 13 не интегрирован; цепочку 13 → 15 проверять отдельно
после объединения. Перенос общей зависимости между ветками — по решению координатора
в рамках запроса пользователя, с записью commit и повторной проверкой затронутой ветки.

В каждой ветке — свои код, тесты и отчёт узла. Разработчики не редактируют общий
реестр потоков в основном checkout. Общие API, registry, readers и UI helpers
менять минимально; самостоятельные общие исправления выделять отдельными коммитами
и отмечать в отчёте для последующего объединения.

## Подготовка перед первым запуском

Подготовку выполнить после команды пользователя на подготовку или запуск потока.
Это необходимая часть запуска, а не отдельная автоматическая задача.

1. Проверить действующие задачи, worktree и владельцев браузеров/аккаунтов.
   Старые каталоги `.worktrees/parallel-*` сохранять. Из них переносить только
   проверенные полезные исследования 11/13; основу брать из актуального main.
2. Закрепить окружение каждого разрешённого потока со своими config, state, очередью архива,
   артефактами, source MCP и browser profile в Dock-owned путях. Для нового узла
   создавать новое состояние; сохранять окружение завершённого кандидата для ревью.
   Секреты и сырые журналы в Git не включать.
3. Для текущего source-запуска проверить MCP каждой задачи в окружении нужного
   узла. Полная привязка native hooks/архива остаётся отдельным незакрытым условием
   native-интеграции и не блокирует source-разработку с неактивированным захватом.
   `plugins/loginom-dock/scripts/launch.sh` выбирает
   `LOGINOM_DOCK_HOME` или глобальный `~/.loginom-dock`; один worktree это не меняет.
   Нужна проверенная привязка к исходникам конкретной ветки и её stateDir.
   Возможность одновременно направить MCP и hooks через настройки отдельной задачи
   ещё не подтверждена. Если потребуется адаптер, оформить его отдельной общей
   подготовкой; не менять глобальный плагин посреди работы потоков.
4. Прочитать фактические revision/hash исходников, runtime, skill, adapter и
   manifest знаний для каждой сессии. Старый staged-каталог пилота не считать
   подходящим новой базе без проверки. Нужные новые карточки готовить в отдельном
   неизменяемом candidate-каталоге; production не переключать. Сборка поставляемых
   артефактов выполняется на VPS по проектному контракту.
5. На живом стенде подтвердить версию, вход и личное хранилище. `/test-1`,
   `/test-2`, `/test-3` были проверены в пилоте; их текущая доступность и отсутствие
   другого активного владельца требуют повторной проверки. Использовать отдельный
   `.lgp` для каждого узла, а также отдельные пакеты диагностики и приёмки.
6. Проверить изоляцию каждой добавляемой сессии: раздельные session IDs, профили,
   файлы состояния, точные workflow refs и сохранение только собственного пакета.
   Завершение одной сессии не должно закрывать остальные. Проверить общий clipboard
   lock. Для текущего source/UI-запуска подтвердить собственные профили и состояние,
   отсутствие активации захвата этих разговоров и явно записать ограничение native
   hooks. Проверка всех hook-запусков и их записей остаётся отдельным условием полной
   native-интеграции; успешный source-допуск не закрывает его.

В worktree Peer памяти определяется его реальным путём. Использовать actor scope,
не подставлять URI памяти основного checkout и не задавать глобальный Peer.
Контекст передаётся через подплан, документы и сообщение задачи; автоматический
доступ к памяти другого checkout этим планом не разрешается.

### Проверенный способ запуска на этом Mac

В каждой постоянной рабочей копии **до создания чата** записана приватная
`.codex/config.toml`. Обычный `mcp_servers.loginom-dock` запускает собственный
`client/bin/loginom-dock.mjs` на Node 24.19.0 с явными config, stateDir, agent,
adapter revision и режимом classic для прямой диагностики Codex.
State и браузерные профили находятся внутри `.dock/stream-runtime` своего worktree;
бинарники браузера и зависимости используются только для чтения.

Настройка `plugins."loginom-dock@loginom-dock".enabled=false` применяется только
к рабочей копии; глобальный установленный плагин и OpenViking не перенастроены.
`config/read` подтверждает локальный слой, source MCP и это значение флага.
Практический probe показал: обычное продолжение уже загруженной задачи не
перечитывает настройку; после повторной загрузки shell получил свой Dock HOME,
но перенаправление штатного plugin hook в него не подтвердилось.

**Ограничение source-разработки:** нативный архив Dock не принят. Для всех трёх
рабочих task ID в глобальной таблице activations нет записей; в source sessions
`archiveActive=false` и отсутствует `archive.json`. Захват этих разговоров не активирован.
Это не доказательство полной изоляции native hooks: отдельный `hooks/list`
перечисляет определения, а исполнение отражают события `hook/started` и
`hook/completed` с threadId. Отсутствие всех фактических запусков пока не доказано.
Не объявлять native-интеграцию или архив готовыми по флагу config. Проверки кода
и UI сохраняются локально; персональная память OpenViking используется в actor scope.
Это отдельный незакрытый пункт подготовки native-интеграции, не приёмка нового узла.

У source-сессий трёх рабочих копий подтверждены раздельные UUID и profile paths,
Node 24.19.0 и единый начальный source hash
`c475d504d9d81f54807c6a3b272351b6fbbe0959d434465e384dc3e0caca190a`.
В живом UI все три разработчика подтвердили Loginom 7.4.2, назначенный аккаунт,
свой каталог и отдельный пакет. Фактическая геометрия каждого окна — 1508×949,
внутренняя область 1508×862 при доступной 1512×949, `viewport:null`.
Полное сохранение/переоткрытие сценариев остаётся проверкой реализации узлов.
Существующие проверки clipboard прошли **5/5**, включая сериализацию отдельных
процессов и удержание блокировки при неподтверждённой вставке.

После изменения JS текущий MCP-процесс не считается обновлённым: новый код
проверяется свежим source harness/bridge из той же ветки с новыми pins и собственным
профилем. Для продолжения разработки не переустанавливать глобальный плагин и
не выполнять общий reload всех MCP приложения.

## Браузеры и общие ресурсы Mac

- Каждый поток управляет только своим экземпляром браузера и своими страницами
  через Dock/Playwright. Разные вкладки одного профиля не изолируют вход Loginom.
  Запуск видимого окна: `--start-maximized`, `viewport: null`, с проверкой геометрии.
- У каждого узла собственный `.lgp`, даже при работе в разных workflow:
  разные workflow одного пакета сохраняют общий риск перезаписи пакета.
  Файлы диагностики и приёмки имеют уникальные имена внутри подтверждённого хранилища.
- Clipboard остаётся общим для Mac. Все потоки используют существующий
  `dock_clipboard_transfer` и **один порт блокировки 46419** до подтверждённой вставки.
  Таймаут не разрешает обход блокировки. Неопределённый результат сначала разбирает
  владелец операции. Прямые системные copy/paste и глобальные клавиатурные жесты
  нельзя выполнять параллельно через Computer Use.
- Проверяющий получает пакет после сохранения и передачи владельцем. Во время
  живого ревью одного узла разработчик не меняет этот пакет и candidate commit.
  Использовать отдельный профиль ревью; при невозможности второго входа передавать
  аккаунт последовательно, сохранив диагностическое состояние.
- Финальные Hermes-прогоны первоначально выполняются **по одному на Mac** с
  отдельным состоянием Hermes и существующей подпиской. Обычная разработка и
  независимая диагностика других потоков могут продолжаться. При перегрузке Mac
  или стенда координатор ограничивает число живых прогонов, сохраняя очереди потоков.
- Общий установленный клиент, global current/previous, плагины, настройки и gateway
  не обновлять во время активных потоков. Общие перезапуски и `pkill` не применять.

## Управление через исходный чат

Разработчики: **gpt-6-astra / medium**. Ревью по запросу: **gpt-6-astra / xhigh**,
в отдельной обычной задаче или вручную пользователем. Это не постоянный четвёртый
поток. Автономная приёмка Hermes: **openai-codex / gpt-5.6-sol / low** через
существующую подписку. Не подменять модели при ошибке, лимите или недоступности.

| Запрос пользователя | Действие координатора |
| --- | --- |
| «Подготовь три потока» | Подготовить worktree и окружения, выполнить проверки изоляции, записать готовность; разработку узлов не начинать |
| «Запусти поток 1» / «Запусти все три» | Завершить необходимую подготовку выбранных потоков, создать отдельные задачи на назначенные узлы и передать подпланы |
| «Статус потоков» | Прочитать актуальное состояние задач и результаты; показать этап, commit, проверки и блокеры |
| «Передай потоку 2: …» | Отправить уточнение в уже назначенную задачу; сохранить границы узла |
| «Запусти финальную приёмку потока 1» | Проверить свободный слот Hermes, закрепить кандидат и выдать запуск этому потоку; после окончания прочитать независимый аудит |
| «Запусти ревью потока 3» | Зафиксировать кандидат и передать diff, подплан и доказательства проверяющему; если разработка идёт, сначала получить checkpoint |
| «Доработай замечания потока 3» | Передать разработчику замечания с требованием живой перепроверки и исправления подтверждённых дефектов |
| «Останови поток 2» | Прекратить выдачу новой работы, получить checkpoint и проверить фактическую остановку; при необходимости использовать доступное управление задачей в приложении |
| «Дай потоку N следующий узел» | Сохранить итог текущего узла, подтвердить освобождение ресурсов и выбрать ближайший доступный пункт полной очереди в новой ветке, новом постоянном worktree и новом чате |
| «Подготовь объединение» | Оценить кандидаты, зависимости и конфликты, подготовить конкретный порядок интеграции и проверок |

Координатор хранит назначение задачи по её ID и использует её фактическое название
из приложения. Сообщения и результаты читаются через средства приложения;
не предполагается, что отдельная задача автоматически передаст итог в этот чат.
Нет фонового опроса или автозапуска: состояние запрашивается при управлении
пользователем или в ходе уже запрошенного действия.

Команда доработки: «Перепроверь найденные дефекты на живом Loginom и после
подтверждения исправь то, что реально недоработано». Неподтверждённое замечание
снимается с доказательством. После правки повторить затронутые проверки; прежнее
ревью не распространяется на изменённый commit автоматически.
При изменении исполняемого кода, контракта или harness требуется финальный
автономный аудит исправленного кандидата. Статус «принят в ветке» допускается
только после заключения проверяющего по окончательному commit и совпадения pins
с доказательствами. Для правок только документации достаточно подтвердить,
что проверенные исходники и harness не изменились, и обновить привязку отчёта.

Передача аккаунта, пакета или следующей задачи выполняется после подтверждённого
освобождения ресурса. Отправленное сообщение «остановись» само по себе не доказывает
остановку агента, браузера или выполняющегося узла Loginom.

## Готовность кандидата и реестр

Этапы: **planned → подготовка → разработка → ожидает автономной приёмки →
кандидат → ревью по запросу → доработка при необходимости → принят в ветке**.
Слияние, публикация и установка
учитываются отдельно. «Кандидат» означает, что разработчик закончил заявленный
объём и его проверки; это ещё не принятие по независимому ревью.

До сдачи кандидат должен иметь:

1. Реализованный объём подплана, актуальный контракт и сфокусированные проверки
   кода, включая регрессии затронутых общих механизмов.
2. Прямую диагностику Codex в реальном UI, сверенную с Help/E2E; исправленные
   причины сбоев до финального Hermes-прогона.
3. Автономную приёмку полного объёма и независимый аудит на закреплённых исходниках
   и harness. Малый полный результат сравнивается с независимым expected;
   отдельно проверяются сохранение, открытие и повторное выполнение пакета.
   Обычный Hermes сохраняет пакет в конце, без обязательного переоткрытия каждого мастера.
4. Commit, отчёт по требованиям, точные версии и хеши, пути доказательств,
   проверенные режимы и оставшиеся ограничения. Файлы кандидата неизменны во время
   приёмки. Итог Hermes, завершение процесса и ручной успех сами по себе не закрывают аудит.

После независимого ревью и устранения подтверждённых замечаний координатор
фиксирует статус «принят в ветке». Если ревью пользователь ещё не запускал,
записать «кандидат, ожидает ревью», даже при успешной автономной приёмке.
Порядок выдачи единственного слота Hermes при ручном управлении:

1. Разработчик завершает прямые проверки и сохраняет в своей задаче checkpoint
   «готов к автономной приёмке» с commit и планом запуска; Hermes сам не запускает.
   Пользователь видит завершение этапа в приложении, а координатор читает checkpoint
   по запросу «Статус потоков» или при следующей команде управления.
2. По команде «Запусти финальную приёмку потока N» координатор проверяет, что
   предыдущий Hermes-процесс завершён, фиксирует владельца слота и передаёт запуск
   нужной задаче. Занятый слот означает сохранённое ожидание до следующей команды,
   без фонового запуска. При недоступности действующего владельца слот не отбирать.
3. В ходе запрошенной приёмки координатор получает её итог через средства приложения,
   проверяет аудит и фактическое завершение процесса, затем освобождает слот.
   Неуспех возвращает узел к прямой диагностике Codex; повторный прогон требует
   исправления причины. Если чат координатора был прерван, состояние восстанавливается
   при следующем запросе по задаче, локальному процессу и сохранённому отчёту.

Текущий слот Hermes этого плана: **не выделен**; это не утверждение об отсутствии
посторонних Hermes-запусков на Mac. Проверка их наличия обязательна перед выдачей.
